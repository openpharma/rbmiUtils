# Design: Resolve issues #50 (`analyse_mi_data()` without known method) and #51 (`tidy_pool_obj()` output format)

**Date:** 2026-07-30
**Status:** Approved design, pending implementation plan
**Issues:** [openpharma/rbmiUtils#50](https://github.com/openpharma/rbmiUtils/issues/50), [openpharma/rbmiUtils#51](https://github.com/openpharma/rbmiUtils/issues/51)
**Upstream context:** [openpharma/rbmi#589](https://github.com/openpharma/rbmi/issues/589), [openpharma/rbmi#494](https://github.com/openpharma/rbmi/issues/494), [openpharma/rbmi#255](https://github.com/openpharma/rbmi/issues/255)

## Background and strategy

Both issues were raised by @wwojciech and are downstream symptoms of the same
gap: rbmi's `analyse()`/`pool()` API carries analysis structure only in
parameter name strings, and rbmiUtils papers over that.

rbmi core is actively discussing absorbing this workflow:

- **rbmi#589** (2026-07-27) requests moving an improved `analyse_mi_data()`
  into rbmi core, explicitly citing rbmiUtils#50 as unresolved.
- **rbmi#494** is a long-running thread on `analyse()` accepting data.frame
  input, where the maintainers acknowledge the ADMI workflow is common across
  the industry.
- **rbmi#255** (visit variable in the pool dataframe) is the root cause of
  #51's fragility.

**Chosen posture: fix now, design for upstream.** Resolve both issues in
rbmiUtils promptly, but shape the API so the pieces can be lifted into rbmi
core largely as-is. If rbmi later absorbs `analyse_mi_data()`, the rbmiUtils
version becomes a thin re-export or is deprecated; the reply on rbmi#589
offers the function upstream rather than defending it downstream.

## Part A — #50: decouple pooling from the imputation method

### Problem

`analyse_mi_data()` requires a `method` object, but users analysing an
existing ADMI dataset may not know the imputation method. Inspection of
`R/analyse_mi_data.R` shows `method` is used for exactly two things:

1. Extracting `n_samples` to validate/filter the number of imputations
   (lines ~178–217).
2. Selecting the pooling class in `as_analysis2()`: bayes/approxbayes →
   `"rubin"`, condmean → `"bootstrap"`/`"jackknife"`, bmlmi → `"bmlmi"`
   (lines ~308–319).

### API change

```r
analyse_mi_data(data = NULL, vars = NULL, method = NULL, fun = rbmi::ancova,
                delta = NULL, ..., pooling = NULL)
# pooling: one of "rubin", "bootstrap", "jackknife", "bmlmi"
```

Rules:

- Supply **either** `method` (unchanged behaviour, fully backward compatible)
  **or** `pooling`.
- Neither supplied → error (current error text extended to mention both
  options).
- Both supplied → error if they conflict (`get_pooling(method) != pooling`),
  otherwise proceed.
- When only `pooling` is supplied, the `n_samples` validation is skipped —
  the data defines the number of imputations.

### New exported helper

```r
get_pooling(method)  # method object -> "rubin" | "bootstrap" | "jackknife" | "bmlmi"
```

Single source of truth for the method → pooling mapping. Used internally by
`analyse_mi_data()`; exported because it is exactly the helper proposed in
#50 and is a small, clean unit to lift into rbmi core for #589. The mapping
logic currently duplicated in the deprecated `as_analysis2()` is replaced by
calls to this helper.

### Documentation caveats

- `"rubin"` is the recommended choice for an ADMI dataset of unknown
  provenance (by far the most common case: Bayesian MI).
- Bootstrap/jackknife/bmlmi pooling assume a specific sample ordering
  (e.g. condmean jackknife expects the original estimate followed by
  jackknife samples) that cannot be verified without the method object; the
  docs state this explicitly.

### Risk to verify first (TDD)

`rbmi::pool()` must work on an analysis object whose `method` is `NULL`.
Pooling is believed to dispatch on the class of `$results` (which is why
this design works at all), but the first test written must prove it. If
`pool()` does require a method object for some paths (e.g. bmlmi's D and B),
the fallback is to construct a minimal stand-in method object internally —
the public API above does not change either way.

## Part B — #51: structured, additive `tidy_pool_obj()` output

### Problem

`tidy_pool_obj()` (`R/tidiers.R`) regex-parses parameter strings such as
`"lsm_ref_Week 16"`. This is fragile, hardcodes `trt`/`lsm` vocabulary that
does not match rbmi's `group` terminology, cannot express real group
variable names or levels, and does not scale to >2 arms. `to_ard()` and
`build_efficacy_table()` consume its output, so format changes ripple.

### API change (additive — nothing breaks)

```r
tidy_pool_obj(pool_obj, vars = NULL, data = NULL)
```

- **All existing columns are kept unchanged**: `parameter`, `description`,
  `visit`, `parameter_type`, `lsm_type`, `est`, `se`, `lci`, `uci`, `pval`.
  `to_ard()`, `build_efficacy_table()`, and external code keep working
  untouched; regression tests assert byte-identical output for the legacy
  columns.
- **New columns**: `group_var`, `group_level_1`, `group_level_2`.
  - Contrast rows (`parameter_type == "trt"`): both levels populated —
    level 1 is the comparator arm, level 2 the reference arm.
  - LSM rows: `group_level_1` populated, `group_level_2` is `NA`.
  - With `vars` + `data` supplied: real names appear (e.g. `group_var =
    "TRT01P"`, levels `"Treatment A"` / `"Control"`). Reference = first
    factor level of `data[[vars$group]]`, matching rbmi convention.
  - Without them: columns fall back to `ref`/`alt` placeholders and
    `group_var = NA`, so the schema is stable regardless of inputs.
- **Descriptions** upgrade to the style proposed in #51
  ("Difference: Treatment A vs Control at Week 16") when levels are known;
  current wording is retained otherwise.

### Deferred (documented, not implemented now)

Renaming `parameter_type` values `"trt"` → `"contrast"` is a breaking change
and is deferred to the release in which the legacy columns are deprecated.
This is stated in the #51 issue response.

### Root cause note

The string parsing exists because rbmi's pool object carries no structured
metadata (rbmi#255). The new schema is the stable contract; if rbmi later
emits structured metadata, `tidy_pool_obj()` swaps its extraction internals
without changing the contract.

## Sequencing and testing

Two PRs, in order:

1. **PR 1 — #50** (`pooling` argument + `get_pooling()`). Feeds the #589
   reply.
2. **PR 2 — #51** (structured tidy output).

Both developed test-first. Key test cases:

- `pooling`-only path produces an analysis object that `rbmi::pool()` pools
  correctly (the Part A risk check — written first).
- Error paths: neither `method` nor `pooling`; conflicting `method` and
  `pooling`.
- `get_pooling()` mapping for all four method classes, including
  condmean type bootstrap vs jackknife, and an informative error for
  unrecognised classes.
- `n_samples` check skipped when only `pooling` supplied; still enforced
  when `method` supplied.
- `tidy_pool_obj()` new columns with and without `vars`/`data`; legacy
  columns byte-identical to current output in both cases.
- Regression: `to_ard()` and `build_efficacy_table()` outputs unchanged.

## Out of scope

- Renaming `parameter_type` values (deferred, see Part B).
- Support for >2 treatment arms (blocked upstream by rbmi#145 —
  `ancova()` does not support it).
- Any change to how ADMI datasets are stored or created.
- Implementing `analyse_mi_data()` inside rbmi core itself (that is rbmi#589,
  a separate effort this design only enables).
